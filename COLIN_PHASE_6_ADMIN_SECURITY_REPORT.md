## 1. Executive Summary

This report details the administrative security architecture implemented under **Phase 6D (Multi-Factor Authentication)** and **Phase 6G (Admin Security & DPDP Compliance)** for the COLIN Admin Control Centre.

To prevent credential compromise from granting unauthorized platform control, all Super Administrators are subject to mandatory Multi-Factor Authentication (MFA). Furthermore, to comply with the Indian Digital Personal Data Protection (DPDP) Act 2023, all Personally Identifiable Information (PII) is masked by default in administrative dashboards, requiring an audited justification endpoint to view unmasked data.

## 2. Native Multi-Factor Authentication (MFA) Architecture

### 2.1 RFC 6238 TOTP Engine Specification
COLIN features an internal, zero-dependency RFC 6238 Time-based One-Time Password (TOTP) engine (`src/server/auth/mfa.service.ts`):

- **Algorithm:** HMAC-SHA1
- **Time Step:** 30 seconds
- **Code Length:** 6 decimal digits
- **Window Tolerance:** ±1 step (30 seconds drift allowance) to compensate for client clock skew
- **Secret Generation:** 160-bit cryptographically secure Base32-encoded secret
- **Authenticator Support:** Fully compatible with Google Authenticator, Microsoft Authenticator, 1Password, and Apple Keychain via standard `otpauth://totp/...` URIs.

### 2.2 MFA Enrollment & Verification Lifecycle

```
[Admin Login] -> Valid Password -> Is MFA Enforced?
  ├─ No  -> Issue Session JWT
  └─ Yes -> Is MFA Configured?
       ├─ No  -> Issue Temporary Setup Token -> POST /auth/admin/mfa/setup -> POST /auth/admin/mfa/confirm -> Active MFA
       └─ Yes -> Issue Ephemeral Challenge Token -> POST /auth/admin/mfa/verify (TOTP / Recovery Code) -> Issue Session JWT
```

#### Step 1: MFA Initialization (`POST /api/v1/auth/admin/mfa/setup`)
- Generates a new 160-bit Base32 secret.
- Generates an `otpauth://` URI and QR code image payload.
- Generates 10 single-use emergency recovery codes.
- Pre-stores the unconfirmed credential in `admin_mfa_credentials` with `is_enabled = false`.

#### Step 2: MFA Confirmation (`POST /api/v1/auth/admin/mfa/confirm`)
- Client must provide a valid 6-digit TOTP code generated by their authenticator app.
- Upon successful mathematical validation, `is_enabled` is set to `true`.
- The 10 emergency recovery codes are activated in `admin_mfa_recovery_codes`.
- An audit event `ADMIN_MFA_ENROLLED` is logged.

#### Step 3: MFA Challenge Verification (`POST /api/v1/auth/admin/mfa/verify`)
- Client submits the ephemeral `mfaChallengeToken` alongside either:
  1. A 6-digit TOTP code, OR
  2. A single-use recovery code.
- If valid, the system issues the full administrative session token (`isMfaVerified = true`) and resets failed login counters.

### 2.3 Single-Use Emergency Recovery Codes
- **Generation:** 10 codes formatted as `XXXX-XXXX` generated via `crypto.randomBytes`.
- **Cryptographic Storage:** Recovery codes are hashed using salted SHA-256 before database insertion; plaintext codes are displayed to the administrator exactly once during enrollment and never stored.
- **Single-Use Invariant:** Once a recovery code is used to authenticate, its database record is updated to `is_used = true` with `used_at = NOW()`.
- **Replay Protection:** Re-submitting a previously used recovery code is strictly rejected with `401 Unauthorized` (`INVALID_MFA_CODE`).

### 2.4 Rejection of MFA Bypass
- Accessing operational admin endpoints (e.g., `/api/v1/admin/metrics`, `/api/v1/admin/properties/pending`) with an unverified challenge token returns `401 Unauthorized`.
- Administrative tokens are cryptographically marked with `{ isMfaVerified: true }`.

## 3. DPDP Compliance & PII Masking Architecture

### 3.1 Statutory Context
Under the Indian Digital Personal Data Protection Act (DPDP) 2023, data fiduciaries must limit employee and operator access to Personally Identifiable Information on a strict need-to-know basis.

### 3.2 Default PII Masking Implementation
All administrative read endpoints for student and owner directories return masked representations of sensitive identity attributes by default (`src/server/utils/pii.ts`):

| Data Field | Plaintext Sample | Masked Representation | Masking Algorithm |
| :--- | :--- | :--- | :--- |
| **Email Address** | `siddharth.mehta@colin.edu` | `s***a@colin.edu` | First character + `***` + last character before `@`, domain preserved |
| **Phone Number** | `+91 98765 43210` | `+91 9*****3210` | Country code + first digit + `*****` + last 4 digits |
| **Aadhaar Number** | `1234 5678 9012` | `**** **** 9012` | First 8 digits redacted, last 4 visible |
| **PAN Card** | `ABCDE1234F` | `*****1234F` | First 5 alphabetic characters redacted |

### 3.3 Audited PII Unmasking Workflow
When an administrator has a legitimate, justifiable operational need to inspect raw student or host contact information (e.g., legal compliance, dispute investigation, emergency safety):

1. **Endpoint Invocation:** Administrator invokes:
   - `POST /api/v1/admin/students/:id/unmask`
   - `POST /api/v1/admin/owners/:id/unmask`
2. **Payload Justification:** Request must supply a non-empty `reason` string (minimum 5 characters):
```json
{
  "reason": "Resolving student safety dispute ticket #4492"
}
```
3. **Authorization Check:** Caller must possess the `VIEW_STUDENT_PROFILES_UNMASKED` or `VIEW_OWNER_PROFILES_UNMASKED` permission.
4. **Audit Trail Recording:** An immutable audit record is immediately committed to `admin_audit_logs`:
   - `admin_id`: Authenticated admin ID
   - `action`: `ADMIN_PII_UNMASKED`
   - `target_entity`: `User`
   - `target_entity_id`: Target user ID
   - `metadata_json`: `{ "reason": "...", "clientIp": "...", "fields": ["email", "phone"] }`
5. **Decrypted Response:** The server returns the plaintext PII strictly for that targeted record.
